⚠ Single generation keeps one object, latest.tar.gz, which every successful upload overwrites. There is no point-in-time restore: older snapshots exist offsite only until the next upload replaces them, and a bad backup replaces a good one on the next successful run. It is the only mode that bounds what cold storage holds without backitup deleting anything.
Deleting offsite objects is not scheduled here. Retention in cold storage is the B2 bucket's lifecycle rule; the life of an object is decided there, per bucket, not per client.
What the snapshot captures

rsync mode only — a targz client ignores these. Changing one affects the next run; snapshots already on disk keep the shape they were written with.

Ownership (uid/gid) is not preserved by these four flags: the receiver runs unprivileged, so every file in a snapshot belongs to the server's backup user. targz snapshots record the numeric owner in the archive instead; rsync snapshots can record it with the Ownership in snapshots setting below.
Group-readable snapshots

rsync mode only. The backup user's own directories are 0750 (owner rwx, group r-x), so an account in the server's group — gid 10001 in the shipped image — can walk into the store without root. What sits inside a snapshot is different: the rsync receiver copies the source's modes, so a source directory at 0700 lands at 0700 and the operator's group still cannot enter it.

⚠ This trades fidelity for access, deliberately. Modes in the snapshot no longer match the source: a 0600 file lands group-readable. And because an unchanged file is a hardlink shared with earlier snapshots, the mode lives on the inode — turning this on also changes the modes of earlier snapshots that share those files. ACLs are not affected by the flag, but an ACL that denies group read will still deny it.
Ownership in snapshots

rsync mode only. The receiver is an unprivileged account (uid 10001 in the shipped image), so it cannot chown — normally every file in a snapshot belongs to the backup account, whatever the source said, and the run still exits 0. Turning this on makes the server record each file's real uid/gid and mode in a user.rsync.%stat extended attribute as it writes, so a restore can put the ownership back without ever giving the receiver root.

Turning this on rewrites this client's authorized_keys line, so it applies to the next run — the client needs no change and no new credentials. Existing snapshots are untouched: a tree written before this was on keeps the backup account as its owner.
⚠ The backups volume must support user extended attributes. ext4, xfs and btrfs do; an NFS volume exposed without xattr support may not. If the receiver refuses them the run fails and the log names xattrs — it does not silently store the snapshot without the ownership. Because the owner is in an xattr, a plain cp or tar out of a snapshot loses it: extract with tar --xattrs, or read the directory with rsync --fake-super.
Restoring: run the pull on the target host and the server's own command adds the flag — rsync -a --numeric-ids -e 'ssh -i <key>' backup@{{.PublicHost}}:snapshots/<snapshot>/ /restore/ as root. Do not add --fake-super to the restoring end: it would write a new pseudo-owner instead of chowning. From an offsite archive, extract it first (tar --xattrs -xzf <archive> -C /stage) and then copy it to the target with rsync -a --fake-super /stage/ root@<target>:/restore/, where the plain root receiver applies the recorded owner. Neither helps a file the client could not read in the first place (a root-owned 0600 qcow2 image): that is a source permission problem, not a receiver setting.
Danger zone

Issues a new SSH key and bearer token. The old key and token stop working immediately, so update the token in the host's cron line after rotating: the next run fails with 401 until you do.

Permanently removes this client, its run history, and its SSH access. The host will need a new client added if you want to resume backups.

⚠ The backup directory and its snapshots are kept on disk: this deletes the client, not its data. Creating a client with the same name later re-uses that directory and inherits those snapshots.
