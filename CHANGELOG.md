# Changelog

All notable changes to Back! It! Up! are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Security

- **Client directories can no longer be shared.** A client's storage directory was derived on the fly from its name, so names differing only in punctuation, spacing or case (`dup a`, `dup-a`, `Dup_A`, `dup/a`) produced one directory and one identical SSH forced command — two clients in one read-write jail, each able to download the other's data. A name with no alphanumeric characters (`..`, `.`, `/`) slugged to `""`, which jailed the client at the backup base directory itself. The slug is now a persisted, UNIQUE column (`clients.slug`), computed once on create and used for every directory path (`authorized_keys`, snapshot listing/download/delete, offsite object prefix, lifecycle pruning). `POST /clients` rejects an empty slug, a slug already in use, and a name longer than 63 characters (the name becomes the directory component and part of the sshd forced command) with a form error naming the conflict; `authkeys.Render` emits no line at all for a client whose slug is unusable, and the slug is validated against an allowlist (`^[a-z0-9][a-z0-9-]{0,62}$`) because it is embedded in `authorized_keys`. Existing databases are upgraded automatically: each row is backfilled from its name, the oldest client keeps the plain slug, later collisions get `-2`, `-3`, … and a slugless name falls back to `client-<id>`. **This separates future writes only — see the upgrade note below for clients that already shared a directory.**
- **Creating a client can no longer break SSH for the fleet, and deleting one can no longer leave its key live.** A backup directory that cannot be created (an over-long name made every `MkdirAll` fail) used to abort the whole `authorized_keys` rewrite, so after that point every create/rotate/delete only logged an error while the file stayed stale — a deleted client kept SSH write access. The name is now capped at 63 characters when the client is created, a directory failure is reported per client without blocking the rewrite, and a failed rewrite after a delete is shown to the operator as an error instead of a success redirect.
- **Deleting a user now ends their sessions.** Admin sessions were keyed only by the username string and never re-checked, so a deleted account kept full admin access until the 12-hour session TTL expired — enough to mint new client keys. Sessions are now bound to the user id, `postDeleteUser` revokes every session of the deleted account, and `requireAdmin` treats a session whose user no longer exists as invalid.

- **A client's own claim of success is no longer taken on trust.** `POST /api/v1/status` accepted `status`, `bytes`, `files` and `snapshot_id` from the bearer-token holder and stored them, so any host holding a valid client token could report a backup that never happened — with any size it liked — and the dashboard showed it as healthy. The token says *which* client is talking, not that anything was backed up. An `ok` is now corroborated server-side before it is recorded: the named snapshot must be listed in the client's own store (rsync: the snapshot directory; tar.gz: the archive, which must also be a non-empty regular file). A claim the server cannot match is recorded as `failed` with `unverified by server: <reason>` appended to its `log_tail` and a line in the server log; the wire protocol is unchanged and the client still receives its `run_id`. The bundled tar.gz client cannot name its archive at all — it streams to `backitup-recv`, which picks the filename server-side, so its report carries no `snapshot_id` — and for that shape the claim is corroborated by the upload itself: a non-empty archive must exist that was written during this run, with the window bounded at both ends (`max(started_at − 15m, now − 2h)`). The client's own `started_at` can only narrow that window, never widen it, because a backdated start would otherwise reach back to any archive the store already holds; the two-hour floor keeps a genuinely slow upload valid, since the archive's mtime is stamped when the upload finishes. Archive *contents* are not gunzipped here — that would read every archive on every report — so a corrupt-but-present archive is still caught by the lifecycle's offsite pass, which reads it anyway.
- **The dashboard no longer reports overlap as health.** Client health was derived from the newest run row, and an `overlap` row (cron fired while the previous backup was still running) fell through to "ok" — and refreshed the timestamp while doing it. A client whose backup had been overrunning its schedule for hours, and whose last real backup was hours old, therefore read "ok / just now", which is the case where the truth matters most. Health is now aged from the client's last **successful** run (`DeriveHealth` takes it explicitly; `LastSuccessfulRun` / `LastSuccessfulRunAllClients` supply it): a fresh overlap after an old success is `stale`, overlap-only history with no success yet is `never`, and only a success inside the cadence reads `ok`. The dashboard also names an overlap instead of presenting it as a backup (`overlap 2m ago`, no size), and the stale-alert pass uses the same rule.

### Fixed

- **A client that only ever overlaps can no longer read healthy**, and an overlap is labelled as such on the dashboard instead of being shown as the newest backup. See the security entry above for the mechanism.
- **Retention actually runs when the source does not change.** A deduplicated offsite upload was skipped without being recorded, so the snapshot never became "offsited" and the hot pruner protected it **forever** — an unchanged directory grew the hot store by one snapshot per run, whatever `retention_days` said. The duplicate is now recorded as a dedup row (`offsite_objects.dedup_of`, additive migration) that names the remote object already holding that content: the snapshot may be pruned, offsite verification checks that real object instead of a path that was never uploaded, the offsite pruner never counts a dedup row as the newest object (which would have made the real object of that content deletable), and deleting an object removes the dedup rows that pointed at it. A dedup record protects a hot snapshot only while the object it names is believed present, and neither does a record whose object the verification pass reported `remote_missing` — "offsited" now means "the content is somewhere else", not "was uploaded once".
- **A failed prune is no longer reported as a clean pass.** `pruneHot` logged and swallowed delete errors, returned nothing, and so `RunOnce` reported success while the hot store kept everything the pruner could not remove. It now returns `deleted`/`failed` counts and the first error: the counts are logged per client and a failure makes the lifecycle pass return it (verification and alerting still run first).
- **A corrupt timestamp can no longer delete a recent offsite object.** Every timestamp column was parsed with `x, _ = time.Parse(...)`, so a malformed `uploaded_at` became year 1 — older than every horizon — and offsite pruning deleted the object as "ancient". Offsite rows that cannot be dated are now skipped with a loud log (the row is kept, and kept out of the pruner's reach) and `LatestOffsite` returns the error; the remaining parse sites are explicit too (`parseStoredTime`/`displayTime`), so no discarded error is left in the store.
- **Offsite staging no longer fills the system temp dir.** rsync archives were written with `os.CreateTemp("")` — the system temp dir, often a small tmpfs — and every archive of a pass was removed only when the pass ended, i.e. N × snapshot size of scratch. They now go to `BACKITUP_STAGING_DIR` (default `<backup dir>/staging`) and are removed as soon as each upload finishes.

### Upgrade notes

- **The client-directory split is forward-only; pre-existing colliding clients keep sharing one directory.** Before this release a client's directory came from its name, so two clients whose names slugged alike (`dup a` and `dup-a`) wrote into *one* directory. The migration gives the later client a new slug, which changes where it writes *from now on*, but it cannot move its history: snapshots in that directory were written by one ssh user with timestamp-only ids, so they are not attributable to either client, and an automatic move would guess and could delete data. Left as-is, the client that kept the plain slug still reads and writes the shared directory and prunes it under its own retention policy, and the other client's existing snapshots there are stranded (never listed, pruned or uploaded again); its offsite default prefix also changes (`dup-a` → `dup-a-2`), so its existing cold objects are reported `remote_missing`. **On upgrade, check the server log for `WARNING: legacy client slug collision`** — one line per affected pair, naming both clients, the retained slug, the new slug and the shared directory. To quarantine it: stop the server, rename that directory aside (e.g. `mv /srv/backups/dup-a /srv/backups/dup-a.quarantine`), start the server so the remaining client begins with an empty directory, then inspect the renamed copy by hand and re-upload whichever client's data you keep.

## [0.1.0.0] - 2026-06-22

### Added

- **Credential rotation** — admins can now regenerate an existing client's SSH keypair and bearer token from the client detail page (`POST /clients/{id}/rotate`). The old credentials are invalidated atomically; run history and all other settings are preserved.
- Rotation result page re-uses the one-time secrets display, showing the new private key, token, and cron line — with a visible warning when the SSH `authorized_keys` file could not be updated immediately (credentials remain valid in the database; `authorized_keys` self-heals on next client edit or server restart).
- Schema migration: a `version` column (INTEGER NOT NULL DEFAULT 1) is added to the clients table. Existing databases are upgraded automatically on first startup. This column guards against double-submit races by using compare-and-swap semantics on every rotation — a 409 Conflict is returned when two concurrent rotation requests are detected.

### Changed

- SSH key generation and token hashing extracted into a shared `generateClientCreds` helper used by both client creation and rotation, eliminating duplicate credential-generation code.
- The `RotateClientCreds` store method now accepts the caller's observed `version` and only updates the row when it matches, incrementing the version atomically on success.
