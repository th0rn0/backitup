# Changelog

All notable changes to Back! It! Up! are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added

- **A per-client `group_readable` setting makes an rsync snapshot readable by the server's group, and the client page says plainly what that costs.** `rsync -a` copies the source's modes, which is the right default but which leaves an operator locked out of a private source tree: a source directory at `0700` lands at `0700` inside the client directory, so nobody but the backup user can enter it. Turning the setting on passes `--chmod=Dg+rx,Fg+r` to the receiver, so directories land group-traversable and regular files group-readable **as they are written** — no second `chmod` walk and no second failure mode. It is deliberately **not** a fidelity setting and the page says so: modes in the snapshot no longer mirror the source (a `0600` file lands `0640`-style), and because an unchanged file is a hardlink shared with earlier snapshots the mode lives on the inode, so turning it on also changes the modes of **earlier snapshots** that share those files. ACLs are unaffected by the flag, but an ACL that denies group read still denies it. `clients` gains `group_readable` (migration v6, default 0, so an upgraded database keeps producing the snapshots it already did), saved by its own form (`POST /clients/{name}/group-readable`) rather than the fidelity form, and carried to the client through `GET /api/v1/config` so the run learns it; a `targz` client is refused with a flash, because its receiver has no snapshot directory to widen. The run log names it (`group readable: --chmod=Dg+rx,Fg+r — modes in this snapshot are widened for the server's group, so they no longer mirror the source`) so "did my setting reach the client" is answerable without reconstructing the argv. **Offsite is unaffected and measured:** the archive is built by the app as uid 10001 and uploaded as one file, so the widened modes travel inside it and an unchanged tree still produces an identical archive checksum, i.e. dedupe still works (`TestGroupReadableSnapshotArchivesTheSameAsAnUnchangedTree`). Tests: the argv with the setting on and off (no rsync needed), a real transfer of a `0700` directory holding a `0600` file producing `0750`/`0640` with the setting on and `0700`/`0600` with it off (today's behaviour, no change), a second unchanged run hardlinking the file — same inode, widened mode — rather than re-copying it, the store round trip, the migration leaving an existing client off, `/api/v1/config` carrying the key, and the page rendering the box with the hint that states both costs.

### Changed

- **The hot store's two server-owned directories are `0750`, and an existing store is healed to that at startup — so an account in the backup user's group can read backups without root.** `<clientDir>` and `<clientDir>/snapshots` were created `0700`, which is what stopped a local account traversing into the store; both are now `ClientDirMode` (`0750`), owned by the app's uid/gid (10001 in the shipped image), and the decision behind it is that **the group is the control**: anyone in gid 10001 on the backup host can read every client's backups, with no per-client permission state. That cost is documented in the README's security model, the directory-permissions section and the client page rather than left implicit. The change alone would have done nothing for an existing install — `MkdirAll` never touches the mode of a directory that already exists — so `ReconcileClientDirModes` widens those two directories to `0750` when they are **owned by the server's own uid** and currently more restrictive, and runs at startup, after a client is created, and when a client is loaded for a run. A directory owned by **another uid** (the bind-mount or root-owned-named-volume misconfiguration) is left exactly as it is, with one log line naming the client and the owner: silently `chmod`-ing a tree somebody else owns is worse than a legible failure. The app-data directory — the SQLite database and every token hash in it — stays `0700` and is not part of this. Deliberately unchanged: the offsite staging directory (`internal/mode/rsync/server.go` `stagingDirFor`) stays `0700`, because it holds `os.CreateTemp` archives at `0600` that are removed after upload and widening it would gain nothing; everything *inside* a snapshot is still written by the rsync receiver, which copies the source's modes unless the client sets `group_readable`. Tests: both directories `0750` and owned by the server's own uid/gid after creating an rsync client, the single directory of a `targz` client likewise, the app-data directory still `0700`, a `0700` store written by the previous build at `0750` after one reconcile pass with a log line naming the client, a foreign-owned directory left alone with exactly one line, and a directory that is already group-traversable not narrowed.

- **The rsync hot tier can now capture what `-a` leaves behind, per client: sparse holes, in-tree hardlinks, ACLs and xattrs.** Thorno asked for "ALL files", and an audit of the rsync path at `86de926` measured four things lost on every run with the client's own flags: a source tree of 1.9 MB on disk with a 1 GiB `truncate`d hole became a **956 MB** snapshot (no `-S`); an in-tree hardlink pair landed as two inodes, storing the data twice (no `-H`); ACLs and xattrs were dropped entirely (no `-A`/`-X`); and ownership arrived as the receiver's uid 10001 with exit status 0 and no warning. `clients` gains `preserve_sparse`, `preserve_hardlinks`, `preserve_acls` and `preserve_xattrs` (migration v5, all defaulting to 0 so an upgraded database keeps the invocation it was already sending), surfaced as four checkboxes on the create form and in **Settings → What the snapshot captures** with a one-line cost note each. Sparse is **on** for new clients — argued in the PR as a straight win: it changes only what the snapshot holds, a qcow2 image that is sparse on the client must stay sparse on the server or the hot tier costs its apparent size, and it measured 1.0 GB → 3.0 MB on the same tree — while the other three stay off (`-H` costs a pass over the file list, `-A`/`-X` are metadata nobody asked for by default). A client with every setting off sends the byte-identical invocation `86de926` did. **Verified against the real jail, not a reading of rrsync's table:** the client's rsync sends `-lHogDtpAXrSe.iLsfxCIvu` (measured through a logging forced command), all four letters are in rrsync 3.5.0's `short_no_arg` allowlist (the recv image now ships rsync/rrsync 3.5.0 on Debian trixie), and a real transfer through the jail returns 0 with holes preserved (2,105,344 bytes on disk for a 1,076,887,573-byte tree), one inode for the hardlink pair, and `system.posix_acl_access` plus `user.*` intact — including across a `--link-dest` incremental run and for a file modified between runs, which is the EPERM case the ticket worried about (the receiver owns what it creates, so it can set the ACL; measured, not assumed). **Refusal is legible:** a receiver that refuses a flag kills the transfer before a byte moves and rsync reports only `connection unexpectedly closed … protocol data stream (code 12)`, so the run now parses the receiver's own refusal and names the setting — `the receiving side refused -A (POSIX ACLs): turn off the "preserve_acls" setting for this client — it said "option -A has been disabled on this server."` — in the error and the run log (and therefore in the incomplete marker's reason). **Ownership is documented, not silently dropped:** the receiver is unprivileged by design, `--fake-super` was measured to work through the jail (`user.rsync.%stat` = `100664 0,0 1000:1000`) but rejected for now because it changes the shape of every snapshot and makes every restore depend on remembering `--fake-super`, and the README plus the client page say that the `rsync` hot tier does not preserve uid/gid while `tar.gz` archives do. Sockets, FIFOs and device nodes stay out of scope on purpose (`rrsync` adds `--drop-D` for any jail other than `/`) and are documented as correct. Tests: the argv for every combination including all-off, sparse measured on disk for both settings (134,225,920 bytes → 16,384 bytes for a 64 MiB hole), inode identity with `-H` on and off, ACL/xattr preserved with the settings on and absent with them off, a refusing receiver producing an error and log naming the flag, the store round trip, `preserve_sparse` form → `GET /api/v1/config` → client decode, the migration leaving an existing client all-off, and the create/settings pages rendering the boxes with sparse pre-ticked.

- **A third offsite upload scope, `single`, keeps exactly one object per client — the only mode that bounds what cold storage holds while backitup still deletes nothing.** `all` mirrors every snapshot as its own object and `latest` uploads one per pass, but since PR #40 nothing in backitup expires an object, so "upload only the newest" bounds the work and not the bucket: every earlier object lives until the bucket rule reaches it. The only way to hold one copy without reintroducing offsite deletion is to write to a **fixed name**, so a `single` client's object is `<bucket path>/latest.tar.gz` whatever its snapshot or mode (`model.OffsiteObjectName` owns that rule and is used by the uploader, the verification listing and the server's download/delete routes alike). The overwrite cannot destroy the copy it replaces: the archive is uploaded to `latest.tar.gz.part` (`rclone copyto --retries 1`), then moved onto the live name with `rclone moveto --retries 1` — a server-side copy plus a server-side delete on B2, so no bytes cross the wire twice and the destination only changes once the copy has completed — and only after the move lands is the bookkeeping rewritten (`store.ReplaceSingleOffsiteObject`, one transaction that deletes this client's rows for that remote and inserts the new one). A failed transfer therefore leaves the previous object and its row untouched, and a failed move replaces nothing and removes only the staging object. Superseded rows are **deleted, not marked superseded**: a row is read as "the remote holds this", the hot pruner deletes on the strength of it and the UI offers its object for download, so a retained row about content the fixed name no longer holds would be the false claim this mode exists to avoid — the upload history an operator wants is already in `offsite_runs`. `rclone lsf` verification looks for the fixed name and reports `remote_missing` as it does for per-snapshot objects. The prune guard needed one extra condition: with `single`, at most one snapshot is ever recorded offsited, so the freshness rule deletes hot snapshots strictly older than the snapshot the fixed object holds and keeps everything newer — but only when the **last offsite upload succeeded**. A failed (or still running) upload leaves the row exactly as the last success left it, so the pass treats the copy as stale and prunes nothing, saying so once per pass (`keeping all N snapshots: the last offsite upload failed (…)`); `ListOffsiteRuns` gained an `id DESC` tiebreak so "which upload ran last" is a property of the rows, not of SQLite's return order. The UI says what the mode costs next to the selector (one generation, no point-in-time restore, a bad backup replaces a good one on the next successful run), and the README's upload-scope table, retention rules and restore section name the fixed object. `all` and `latest` are untouched and covered by a regression test that asserts they still name objects after their snapshots and never move one. Evidence: two successive uploads leave one object holding the second payload and one row naming the second snapshot; a failing upload and a failing move each leave the previous object and row intact; a deleted object is reported missing; with `single` the prune deletes only what is older than the held snapshot (even past the horizon) and keeps what is newer; a failed upload prunes nothing; and the rclone invocation order is asserted (staging name, then the move) as well as run end to end against a real rclone over a crypt-wrapped local backend.

- **Offsite encryption is now something the product offers, not something you hand-wire.** `internal/model` had eight backends and no `crypt`, so `OffsiteRemote` could only ever name a plaintext one — an operator who wanted the README's "the provider only ever sees ciphertext" had to write a `[crypt]` section into `rclone.conf` by hand, and lost it on the next UI action (see the fix below). There is now a **crypt** backend, listed first in the Add-remote form: it takes the **plaintext remote it wraps** (validated to exist — either a remote defined here or a section you wrote into `rclone.conf` yourself — to be a plaintext remote, and not to be itself), optional **directory-name** encryption (rclone's `directory_name_encryption`, on by default), **filename encryption** (standard / obscure / off — rclone's default, standard, stays the effective default when the line is omitted), and the two key parts (`password`, `password2`). The generated section is `[<name>] type = crypt` with `remote = <parent>:`, which is what makes rclone encrypt on the way to the provider, and the plaintext parent cannot be deleted while something encrypts it. Pick the crypt remote as a client's offsite destination and uploads, downloads, deletes and pruning all go through it — the destination list labels it "Encrypted (rclone crypt)", and lifecycle's upload path is covered by a test that asserts rclone is invoked as `copyto <local> <crypt>:<path>` and never against the plaintext remote.

### Changed

- **Offsite storage is Backblaze B2 only — the generic rclone remote types are gone** (Thorno, 2026-11-19: *"Only Backblaze B2 compatible."*). A remote is created as `b2` from a form that asks for exactly what B2 needs — **keyID** (`account`), **applicationKey** (`key`), **bucket**, optional **path prefix** — with no provider selector; a **crypt** remote wrapping one is still creatable from the same page and stays the default recommendation, because B2's server-side encryption does not protect the backup from B2. `POST /settings/remotes` answers **400 naming the offending value** for any other type (`s3`, `s3-compat`, `drive`, `sftp`, `webdav`, `azureblob`, `ftp`, rclone's `local`, or a typo), under either the `backend` or the `type` field, and stores nothing. The bucket and prefix are now fields of the remote, so an object is addressed as `<remote>:<bucket>/<prefix>/<client path>/<object>`, and a crypt section's `remote =` line carries its parent's root so the bucket is actually honoured. Rows an older backitup created with another backend are **kept and marked unsupported** (migration v4 adds `remotes.unsupported` and sets it for every non-b2/crypt row): the page shows "unsupported remote type — recreate as B2", the edit form is replaced by that banner and a POST is refused, and the lifecycle neither uploads through them nor verifies against them — while their hot copies stay, because nothing was tiered, so the pruner must not treat the client as offsite-less. `model.BackendLocal` survives for tests only: the offsite end-to-end proof (upload → dedupe → verify → decrypt) runs against a real rclone `local` backend behind a real crypt wrapper, it is absent from `model.Backends` so no form offers it, and the create handler refuses it. README's offsite section names B2 as the only provider, with the keyID/applicationKey/bucket steps and an upgrade note for the bucket moving from the client path onto the remote.

- **Offsite retention is the B2 bucket's lifecycle rule now, and backitup no longer has an offsite horizon of its own.** Two settings decided how long cold copies lived — `offsite_retention_days` (an independent horizon, D8) and `disable_offsite_pruning` (a flag that switched `pruneOffsite` off so a provider's policy could be used instead). Both are gone, along with `pruneOffsite` itself and the per-client log lines that explained it. The reason is that a second decider is a second way to be wrong: the bucket already expires objects, and a local horizon that disagreed with it either deleted data the operator had configured the bucket to keep or claimed to keep data the bucket had already removed. What the server does now is upload, verify, dedupe and list — one lifecycle pass deletes **no** offsite object at any age, and no code path reads `offsite_objects` rows to decide a deletion. A migration drops both columns (`clients.offsite_retention_days`, `clients.disable_offsite_pruning`) in one transaction; they are named in `droppedColumns`, so the rebuild that removes them is the same table-swap the rest of the schema uses and the "unexpected column" refusal stays armed for anything else. The four tests that asserted offsite pruning (`TestRunOnceOffsiteRetention`, `TestRunOnceReportsDisabledOffsiteRetention`, `TestRunOnceReportsDisabledOffsitePruningFlag`, `TestPruneOffsiteKeepsObjectWithMalformedTimestamp`) now assert the opposite: a pass over objects 8 days, 40 days and 400 days old — plus one whose `uploaded_at` cannot be parsed at all, which the removed pruner read as year 1 — deletes nothing and leaves the row count identical (8 rows before, 8 after), and a client with a remote gets no retention line in the log. `TestRunOnceOffsiteAndPrune` still covers the upload path and now also covers dedupe (an unchanged tree records `dedup_of` with 0 bytes and no new object) and asserts the lifecycle pass deleted nothing offsite. **Unchanged on purpose:** hot retention (`retention_days`, including the ordering/age fixes), the un-offsited guard (`offsiteOn && !offsited[id] → keep` — a data-safety rule, not a retention rule), dedupe, the manual offsite delete in the UI (`postBulkDeleteOffsiteObjects`, `ForgetOffsiteObject`), and offsite verification. Verification is the check that matters more now: with objects expiring out of band, `remote_missing` is what tells you a rule ate something it should not have, and a missing object stops its snapshot counting as safely offsite. The server logs one line at startup, once per process: `lifecycle: offsite retention is delegated to the B2 bucket lifecycle rule; backitup will not delete offsite objects`.

### Fixed

- **An offsite-only snapshot no longer reads "missing on disk" in red, and its row can hand the copy over instead of offering to forget it.** Since the pruner deletes a hot snapshot once a strictly newer one is offsite (PR #47), an `offsite_objects` row with no snapshot directory behind it is the designed steady state of a working retention policy — the bucket holds the copy — not data loss. The client page rendered it as a red `missing on disk` badge whose only action was `Delete entry` (`POST /clients/{slug}/offsite/{id}/forget`), which removed the row while the object stayed in the bucket: the one state where cold storage holds the only copy was the one state with no way to fetch it. Now the row reads `offsite only` in the neutral badge (tooltip: retention pruned the hot copy, the bucket holds this copy, and when the last check saw it), carries the same server-side `rclone cat` download the Offsite tab has, and offers `Stop tracking` as a secondary action whose confirmation states that the object stays in the bucket and that backitup will no longer list, download or verify it. While the last verification still sees the object the form requires a second confirmation that names the snapshot (`confirm=<snapshot id>`), and a POST without it is refused with a flash that says nothing was removed. Red `not in the bucket` is now reserved for `remote_missing` — the object the last check could not see — and its tooltip distinguishes "not on disk" from "not in the bucket". The Offsite tab's `Local` column says `offsite only` where it said `deleted`, so no state has two words on one page, one line above the local table explains why such rows exist (rendered only when one does), and the local table's bulk-delete toolbar appears only when there is something local to delete. **The forget is no longer a half-operation:** `store.ForgetOffsiteObject` and `store.DeleteOffsiteObject` both remove the dedupe records that claimed their content lived in the removed object, in one transaction (the existing `DeleteDedupRecords` had no caller at all — neither delete route used it). Left behind, those rows were a chain pointing at a record nobody could read; removed, the snapshot they named stops counting as offsited, which protects its hot copy from the pruner, and the next upload pass gives it an object of its own. Tests: a client with a retained snapshot and an older offsite-only one renders `offsite only` plus the download link and not `missing on disk`; a row whose verification reported the object gone renders the red state with wording that names both losses; forget refuses without the snapshot's name and works with it, with a flash stating that the object remains; afterwards no row — dedupe included — claims an offsite copy of the forgotten object, and a lifecycle test drives the next pass to re-upload the deduplicated run for real. Runbook §2 explains the state and warns that forgetting is not deleting.
- **The dashboard's "on disk" figure is measured from the store now, so an rsync client no longer reads `0 B` beside eleven snapshots.** The client page computed it as `sum(Snapshot.Bytes)`, and `internal/mode/rsync` sets `Bytes: 0` deliberately: rsync reports no per-snapshot size, and summing a hardlinked tree naively would count every unchanged file once per snapshot. The figure was therefore structurally zero for the mode whose snapshots share inodes — and a capacity judgement made from that panel was wrong in the worst direction, reading a full volume as empty. The fix is not to invent a per-snapshot size. A new `internal/diskusage` walks a directory and sums **allocated blocks** (`st_blocks * 512`, each `(st_dev, st_ino)` counted once), which is what `du` reports and what the operator pays for: sparse files are honest and a file shared by ten snapshots costs one copy. The walk is bounded by `Deps.DiskUsageMaxEntries` (default 1,000,000 stat calls) so a pathological tree cannot stall the pass that also does retention; a capped walk **says so** instead of returning a truncated number as if it were a total. The lifecycle pass measures each enabled client **after** that pass's pruning and stores the result in a new `client_storage` table (`disk_bytes`, `disk_partial`, `measured_at`, migration v7 — one row per client, replaced every pass; `DELETE CASCADE` so a deleted client's figure cannot linger in the fleet total). Every page reads the stored row and never walks a tree: the client page shows `On disk (allocated)` with `as of 3m ago`, `≥ 1.2 TB` plus `lower bound: the walk stopped at its entry cap` when the figure is capped, `not measured yet` for a client whose store no pass has measured, and `—` when there is nothing stored to measure — never a confident `0 B` for a client that has simply never been measured. `targz` keeps its real per-snapshot sizes and gets the same total, so the two modes read consistently. The server's own background storage meter (`BACKITUP_STORAGE_REFRESH`) is gone: the fleet figure is now the sum of the same per-client rows, aged at the **oldest** measurement included, with a client that has not been measured counted and shown rather than assumed to be zero (`≥` plus `1 client not measured yet`). **The bound is the lifecycle pass, not a second scheduler:** `BACKITUP_LIFECYCLE_INTERVAL` (5m in code, `1h` in compose) is how often the number refreshes, and the runbook's dashboard section now says exactly that. Tests: hardlinked snapshots measure one inode rather than twice the file; a sparse file measures its allocated blocks and matches `du -sk` on the same tree within the stated 64 KiB tolerance; a capped walk stops at the cap, stores `Partial` and logs the lower bound with the page rendering `≥` and the reason; an rsync client with snapshots renders the stored figure and not `0 B` (and not the tree's real size, proving the request path read the store); a client with no snapshots renders `—`; a client with snapshots but no measurement says `not measured yet`; the dashboard sums two stored figures while its backup directory is moved out from under the server; the store round trip, the cascade delete, and a `user_version` 6 database gaining the table on upgrade.
- **Hot pruning now deletes a snapshot when a strictly newer snapshot is already offsite, instead of requiring an offsite record of that snapshot itself.** The offsite-first guard was per-snapshot (`offsiteOn && !offsited[id] → keep`), which read as data safety and behaved as "retention never fires": a client on `offsite_upload_mode = latest` offsites exactly one snapshot, so every other one had no record of its own and was kept forever, and a run of failing uploads stopped retention entirely while the hot store filled. The guard is now a property of the client's offsite state: `pruneHot` finds the newest snapshot (by `CreatedAt`, ID as tiebreak) whose id counts as offsited and deletes a snapshot only when it is **strictly older** than that one — anything at or newer than the newest offsite copy is kept, nothing offsited means nothing is pruned, and the age horizon still applies on top (the rule narrows `retention_days`, never widens it). Deleting an old copy is safe because a strictly newer copy exists somewhere; the content being offsite in its own right is what the old guard asked for and what no client can guarantee. Logging answers both questions from the pass alone: `pruning <snapshot>: older than the newest offsite copy <snapshot> (<timestamp>)` per delete, and one line per pass with a count when the guard holds snapshots back (`keeping 4 snapshots: not older than the newest offsite copy …`, or `keeping 2 snapshots: nothing is offsited for this client, so there is no copy elsewhere to fall back on`). `pruneLeansOnDedupe` had to move with the rule: the claim a delete leans on is now the record for the newest offsite copy, so an expired dedupe claim that happens to hold that position forces the remote verification before anything is pruned (a stale per-snapshot check would have missed exactly that case). Tests: only-older-is-pruned with uploads healthy, nothing-at-or-after-the-marker with uploads three snapshots behind, nothing offsited at all, offsite disabled (age-only, unchanged), and dedupe rows counting only while their owner object is intact. `TestRunOnceOffsiteFirstProtectsHot` became `TestRunOnceOffsiteFirstRequiresANewerOffsiteCopy`, which pins the motivating case end to end: with `offsite_upload_mode = latest` and failing uploads nothing is pruned and the pass says why, and once the single latest upload succeeds both older snapshots go. Two PR #42/#44 fixtures were re-staged for the new rule (each now puts the dedupe row in the marker position where its claim is what a delete leans on) rather than weakening their assertions. **The trade-off is deliberate and documented in the README:** while offsite is stale or broken the hot store keeps everything newer than the last good offsite copy and grows, so an offsite outage shows up as disk growth plus the log line instead of as retention quietly deleting the only copies. Unchanged on purpose: the newest-snapshot protection, the age/ordering fixes, `pruneIncomplete` and the incomplete marker, dedupe semantics, and offsite expiry (still the B2 bucket's lifecycle rule).
- **Offsite uploads no longer address the bucket twice, and a remote whose bucket the key cannot see is refused at the form instead of failing every upload with `duplicate_bucket_name`.** Thorno's offsite stopped dead: `rclone copyto … "tehHulk-source:tehhulk-source/tehhulk-source/20261123T222033Z.tar.gz"` → `failed to create bucket: Bucket name is already in use (400 duplicate_bucket_name)`, three attempts, 0 bytes, every pass. Two defects in one line. (1) `model.Remote.RootPath` emitted `<bucket>/<path>`, and the path had itself been filled with the bucket name — the field is labelled "Path inside the bucket", so operators type it there and an older build defaulted it to the client's slug — while the client's own directory is *also* named after its slug; a client called `tehhulk-source` on a bucket called `tehhulk-source` therefore wrote to `<bucket>/<bucket>/<snapshot>`. A path that equals the bucket, or begins with `<bucket>/`, is now dropped before the object path is built (`RootPath`), and a client directory that only repeats the bucket is dropped by `model.ObjectDir` — the single join used by the upload path, the verification listing *and* the download/delete routes, so they cannot disagree about where an object is. (2) Nothing checked that the key could see the bucket it was given, so a key without access surfaced only here, as a 400 about bucket creation: rclone's B2 backend creates a bucket when its own lookup does not find it, and the name belongs to someone else's account. `POST /settings/remotes` and `…/edit` now ask rclone before saving — `rclone lsd <remote>:` lists the buckets the key can see, and a bucket that is not among them is refused by name, listing the buckets that *are*, and saying that B2 application keys cannot be widened once created so the fix is a new key scoped to that bucket. A key scoped to one bucket is the configuration we want and cannot enumerate buckets at all (B2 gives it no `listBuckets`), so a failed or empty listing falls back to `rclone lsd <remote>:<bucket>`, which succeeds exactly when the key can address it; only rclone running and refusing is a refusal, and a check that could not run (no rclone on the host, no answer) is logged and the save goes ahead — a machine fault must not make a remote impossible to configure. The check runs against a throwaway 0600 config, so credentials that have not been accepted never reach the shared `rclone.conf`. Finally the upload error is legible: a `duplicate_bucket_name` now records *"rclone could not see bucket "X" on remote "Y", so it tried to create it and B2 refused … create a B2 application key with read and write access to "X""* instead of quoting rclone's `Failed to copy: multi-thread copy…` into the run, which stays in the log at debug level; and the upload is one attempt (`--retries 1`), because a deterministic refusal repeated three times per snapshot per pass per client is noise — the next scheduled pass is the retry. Tests: `RootPath` for `b|b`, `b|b/sub`, `b|sub` and empty; the object path for a client whose slug equals the bucket naming it once; create refused with the visible buckets in the message and nothing stored or written to `rclone.conf`; the bucket-scoped-key fallback accepted; an edit refused with the stored bucket unchanged; and the `duplicate_bucket_name` run error with the upload attempted once. All of them fail on the pre-fix tree.

- **A run that is killed before it can report no longer leaves an unmarked partial snapshot that the listing, the offsite worker and retention all treat as a backup.** The marker fix below covers a run that reaches its own error path: rsync exits non-zero, the client writes `.backitup-partial`, and everything downstream refuses the directory. It does not cover the run that is not given the chance — SIGKILL, host reboot, power loss, a broken control channel, the container OOM-reaped — because nothing arrives from that client at all, so `snapshots/<ts>/` stays on the server with no marker on it and is again indistinguishable from a snapshot. Nothing a client says can be relied on to fix that, so the server decides from its own record: the run opened a `running` row naming the second it started and never reached `ok`, which is all that is needed to say the directory is not a backup. `mode.UnbackedSnapshots` makes that judgement — a snapshot named by an `ok` run is a backup whatever its age; one named by a run recorded `failed` is not; a directory a run is still writing into is left alone, whatever its age; and **one with no run row at all stays a snapshot**, because absence is not evidence (it may have been created outside backitup, or its row pruned by run-history retention — the two are told apart by the row being present, not by its age, and the fallback is deliberately the conservative one). `lifecycle.VisibleSnapshots` is the single place that fetches the history and answers for the lifecycle worker, the dashboard, the client page and the download route, so they cannot disagree. Hiding comes first and deleting second: the directory is out of every listing and every offsite pass from the moment its run is known dead, and reclaimed after the same `DefaultIncompleteAge` hour the marked ones get, logged every pass while it waits (`snapshot <id> is not a backup (run 7 started … is recorded failed: interrupted: …) — hidden from the listing and from offsite; reclaiming after 1h0m0s`) and again on removal (`removed incomplete snapshot <id> left by a run that never reached ok (…)`). Two supporting changes: `RunOnce` now marks runs stuck in `running` as failed **before** it processes any client, so a run that was killed is settled in the same pass that judges its directory rather than one pass later; and a mode declares this capability itself (`mode.RunStartNamed`, implemented by rsync and not by tar.gz, whose archive is named server-side and renamed into place only on success) instead of the caller branching on the mode. Offsite treats an unreadable run history as fatal and uploads nothing, while the display paths fall back to the unfiltered listing and log — a database blip must not hide a real backup, but it must not ship a partial one to B2 either. Coverage: the judgement itself (ok-backed, killed, still-running, overlap-only, pruned history, unattributable name, and the one-minute window either side), a killed run's directory invisible to the client page and its download route while the real snapshot in the same directory is listed and downloadable, the offsite worker skipping it and recording nothing for it, a lifecycle pass reclaiming the old one and keeping the fresh one with both log lines asserted, retention not counting its timestamp as "the newest", and a snapshot backed by an `ok` run whose log has been cleared staying a snapshot. Disabling the guard fails all three layers.

- **A failed rsync run no longer leaves a directory that the listing, the shape test and the offsite worker all treat as a backup.** `runRsync` failing made `Backup` return before `flipLatest` — correct, it is what protects the previous good snapshot — but nothing dealt with the `snapshots/<ts>/` rsync had already created on the server, and that directory is indistinguishable from a snapshot. Thorno's client hit it for real: rsync exit 23 on a 375 GB source because four root-owned `.qcow2` files could not be read (`Literal data: 0 bytes`), leaving four zero-byte files that `List` returned, `VerifySnapshot` accepted (its shape test was "present, at least one entry"), and the offsite worker tarred and could upload to B2 as the client's backup — a listing that says the client is covered when it is not. The client cannot delete the directory itself: it talks to the ingest host through `rrsync`, which is rsync-only and never unlinks a destination. So the run now **marks it**: on a non-zero rsync exit the client writes `.backitup-partial` into `snapshots/<ts>/` with one small rsync of its own, carrying the run's error and the counts rsync reported (`Number of files: 5` is the file list it intended to copy, not a backup size). `List` refuses a marked directory, so nothing downstream can offsite, count or display it; `VerifySnapshot` reports it as `incomplete: rsync: exit status 23 …` rather than passing it; `mode.ServerMode.ListIncomplete` is the one caller that sees it, and the lifecycle reclaims it an hour after it was marked (`removed incomplete snapshot <id> left by a failed run on …`), because a half-copied tree that no listing can see is also a tree nothing would ever delete. Absence of the marker still means "normal", so every snapshot written by an earlier version keeps working. Two further guards: `VerifySnapshot` now also rejects a snapshot whose top-level regular files are all 0 bytes when it is flat (no subdirectory to look inside, ≤64 files — the sample is deliberately biased towards silence so a real backup is never accused), and a failed run reports **no** counts — the log says `rsync counted 5 files / 0 B … NOT a backup`, while the reported run carries `files: 0, bytes: 0`, so a failed run cannot read as a plausible "synced 4 files". `latest` is untouched on failure, and a failed `flipLatest` is deliberately not marked (the tree is complete; only the pointer did not move). Coverage: the client path is exercised against a real rsync (exit 23 reproduced with a 0000 file, via an `ssh` stand-in that runs the remote command inside a temporary jail) asserting no listable snapshot, no marker-less directory, `latest` unchanged and the previous good snapshot still verifying; a lifecycle pass over a marked directory offsites only the good snapshots and reclaims the marked one; a legitimately empty source directory still backs up normally (the negative case, on both builds); and the dashboard shows the run `failed` with rsync's own error text on its log page.

- **A run that deduped against an object the bucket had expired no longer claims an offsite copy that does not exist, and its hot copy is no longer pruned on the strength of that claim.** Delegating offsite retention to B2's lifecycle rule made local dedupe dangerous, silently: an unchanged tree does not upload, it records `dedup_of` with 0 bytes against the previous run's object, and that row is an *inference* — "my content lives in that object" — which the bucket can make false without backitup hearing about it. Once the object expired, the dedupe row still read as "a copy exists elsewhere", so `pruneHot`'s un-offsited guard let the hot snapshot go and the client was left with **no copy anywhere** while the database said otherwise; nothing surfaced it until a verify happened to run, and by then the last copy was gone. Three changes, one rule — a claim nobody has re-checked is not permission to delete the only copy. (1) The remote existence check now runs **before** the prune instead of after it, so the listing that answers "is it still there?" is part of the pass that deletes; it is forced past the hourly throttle when a delete would be justified by a dedupe claim (one cheap `rclone lsf` per pass per such client), because that is the one record that goes stale without backitup acting. (2) The same reconcile marks a dedupe row whose owner object the listing reports gone as `remote_missing` — "needs re-upload", not "offsited" — and says so once per client per pass: `offsite object <owner> referenced by run <snapshot> is gone (expired by the bucket lifecycle rule): re-uploading`. (3) The upload pass reconciles before it decides anything is already on the remote, so an expired owner is never deduplicated into again and the dependent run is re-uploaded — or, when the owner is itself gone from hot and cannot be re-uploaded, uploads an object of its own. If a re-upload is impossible at all (client removed, directory gone) the hot copy simply stays: the only-copy rule wins over retention. Re-recording an object now clears `remote_missing`/`remote_verified_at`, so a re-uploaded snapshot becomes offsited again instead of turning un-prunable and being re-uploaded every pass. Tests cover the whole sequence (upload, dedupe, expire the owner out of band, a pass that flags it and keeps the hot copy, the next pass re-uploading it, later passes silent), the owner-cannot-be-re-uploaded case (the run gets its own object, and its hot copy survives until it does), and the healthy case (an intact owner still dedupes and re-uploads nothing across repeated passes). Two existing tests needed fixtures describing a remote that really holds what their rows claim, now that a pass believes the remote before it deletes; the shared archive helper also pins the source mtime that tar records in the header, which removes a pre-existing flake that made "identical content" depend on both archives being built inside the same wall-clock second.

- **Hot retention no longer deletes the newest snapshot, and no longer ages a tar.gz archive by its mtime.** Two defects with one reporter: Thorno's "backitup doesn't seem to be deleting backups from disk". `List` for both modes built its slice with `os.ReadDir`, which returns entries sorted by filename — and since every snapshot id begins with its timestamp, that is **oldest first** — while `pruneHot` read position 0 as "the newest, never delete it". That guard was only ever as good as its caller's ordering, and the ordering the modes themselves produced was the opposite one: list oldest-first, protect the oldest, delete the rest — reproduced on the pre-fix binary with `retention_days=1` and two tar.gz archives, the one taken hours ago was removed and the six-day-old one kept, with the log line `hot prune: deleted=1 failed=0` reading as a clean pass. Separation is now the contract rather than a convention: each mode's `List` returns snapshots newest-first through one shared `mode.SortNewestFirst` (timestamp descending, id breaking ties), `pruneHot` picks the newest by `CreatedAt` instead of by position so the guarantee does not depend on its caller, and `verifyLatest` does the same (it was integrity-checking whichever snapshot happened to sort first). The second defect fed the first: a tar.gz snapshot's `CreatedAt` was its **file mtime**, so any `cp`, volume copy, restore, file-level sync or archive extraction rewrote the age that decides deletion — an old archive copied onto the volume looked new forever and retention never fired on it (`CASE A: old ID, fresh mtime → still present`), while an archive whose mtime was preserved from the source looked ancient and was pruned immediately. `List` now parses the timestamp out of `backup-<ts>-<seq>.tar.gz`, the same way the rsync mode already parses `<ts>`; `backitup-recv` stamps that name on the server's clock as it writes the upload, so it is the age the snapshot actually has. mtime is used **only** for a file whose name is not that shape (a hand-placed archive, an older layout), and `Bytes` still comes from `info.Size()` — that is what the client page shows. Status corroboration is deliberately unchanged: `POST /api/v1/status` for a tar.gz client that cannot name its archive still asks "did bytes land on this hot store at or after this run started", which is the file's write time, not the snapshot's age — the two now differ, and a slow upload finishing two hours after its start must still corroborate. Reproduced-then-fixed tests cover both directions for both modes, an oldest-first slice handed straight to `pruneHot`, and the list ordering itself; the offsite-first rule (`offsiteOn && !offsited[id] → keep`) is untouched.

- **A refused or failed snapshot delete now says why on the page.** Both failure paths threw the reason away, so from an operator's chair they read identically as "I clicked delete and nothing happened" — which is the report we got ("there appears to be an issue where I cant delete backups from the UI"). A delete that genuinely failed on the filesystem (`unlink …/backup-….tar.gz: permission denied`) redirected with the flat flash `delete failed`, and an id the validator refuses answered a bare `404 page not found` that named nothing; in both cases the mechanism existed only in the container log. The single-snapshot route now carries the error's own text — `delete failed: unlink /…/backup-….tar.gz: permission denied` — because these are admin-only pages and the path in it is what identifies the failing tier, and an invalid id now redirects with `delete refused: invalid snapshot id: "…" is not a targz snapshot name` instead of 404-ing. The bulk hot-delete's bare `400 invalid snapshot id` becomes a flash that names every refused id and states that **nothing was deleted** (the all-or-nothing rule is unchanged), and a partial failure reports the count that succeeded next to the ids that failed and the first cause, instead of `some deletes failed`. The offsite bulk path had a flash but no information in it: it now reports the succeeded count, the failed ids with a cause, and any id it declined to address (those used to be skipped silently), and the single offsite delete carries its rclone error too. The offsite "Delete selected" path is now covered end to end by a test that drives the form route against a stub `rclone` and asserts the deletefile calls, the dropped tracking records and the flash. Nothing about what is deleted, the validation rules or the retention logic changed. **Status codes:** an invalid id in the bulk form answers `303` with the refusal flash where the bulk-delete security fix above made it `400`, and the single route answers `303` + flash where it answered `404`; a refused or failed delete still deletes nothing, which those security regression tests keep asserting — now against the rendered page as well as the store.

- **Every rsync client no longer logs a false integrity warning on every lifecycle pass.** rsync snapshots report `Bytes: 0` on purpose — summing a hardlinked tree is a full walk and the lifecycle may not block on it — and the integrity pass read `Bytes == 0` as "the snapshot is empty", so it logged `INTEGRITY WARN: latest snapshot <id> is empty` on every pass for every rsync client, forever. The line was not the cost: a real finding was indistinguishable from it, and it read as "your backup is broken" on first run. Integrity is now the mode's own business (`mode.ServerMode.VerifySnapshot`): rsync samples the snapshot's shape — the directory must still exist, must hold at least one entry (one `ReadDir` of its top level, never a walk), and `latest` must still resolve to a snapshot, since a dangling one silently turns the next `--link-dest` run into a full copy — while tar.gz still reads the archive end to end so gzip/CRC damage surfaces. A healthy rsync client now logs nothing; an empty directory, a vanished one or a dangling `latest` is reported as `INTEGRITY FAIL on <id>` naming what is wrong, and nothing anywhere compares `Bytes` any more.

- **A status verification that could not run no longer records the run as failed.** `POST /api/v1/status` corroborates a claimed `ok` against what is really on the hot store, and that check runs under the request's store deadline. When the deadline had gone — a store stall of a few seconds, exactly the case the store-timeout work in this release is about — the listing went ahead anyway, read nothing it could vouch for, and the client's snapshot was reported as *absent*. The run was then written to history as `failed` with `unverified by server: snapshot "…" is not in the client's store`, so a database hiccup became a durable fact about the client's backup that no later success edits out: the operator debugs a backup that worked. On the pre-fix binary a test that hands the verifier a spent deadline stores `failed` with that message. "Could not verify" and "verified and it disagrees" are now different outcomes: the check stops at a spent deadline (before *and* after the listing, since a listing that finishes late was produced by a stalled store), the failure is classified with the same classifier the handlers use (`classifyStoreFailure`), and the run keeps the client's own report with `unverified by server: verification could not run: <the store's own error>` appended to its `log_tail` — the underlying error, not a flattened message, in the row and in the server log with the bound that expired. There is no third status to use for the case: `runs.status` is `CHECK`-constrained to `ok`/`failed`/`overlap`/`running` and health, the dashboard and the alerts all read it, so an `unknown` would be a schema migration plus a new health state, not a label. A verification that **did** run and cannot find the claimed snapshot is unchanged: still `failed`, same message.
- **`rclone.conf` regeneration no longer destroys sections backitup did not write.** The file was rebuilt from the `remotes` table on startup and after every create/edit/delete, so a hand-written `[crypt]` section vanished the next time anybody touched the UI — the exact opposite of the policy the README advertises. The writer now owns only what it generates: sections whose name matches a remote in the database, emitted in one marker-delimited block at the end of the file (so a restart replaces its own block instead of appending a second copy of a section name rclone would refuse). Everything else — the operator's sections, comments, blank lines, ordering — is preserved byte for byte. A file written by an older backitup has no markers, so ownership is decided by name and those sections are migrated into the block rather than duplicated. The startup write, `POST /settings/remotes`, edit, delete and a second startup are each covered by a test that reads the file back and asserts the hand-written section is untouched, including that deleting the last managed remote leaves the operator's content alone.

- **Ownership of `rclone.conf` now consults the file, not only the database.** Two ways an operator's own section could still be lost by doing the right thing: creating a remote in the UI named after a section they wrote (the realistic case is a remote literally called `crypt`) rewrote that section and took its key with it, and deleting a managed plaintext remote left any hand-written `[crypt]` that wraps it pointing at a remote rclone can no longer resolve. `POST /settings/remotes` now refuses a name the file already defines and that backitup does not own, naming the section and telling the operator to rename or remove it there (it does not silently rename their section — every client, cron job and script that uses it would break just as quietly); the delete guard now also scans the file for a section whose `remote` setting references the remote being deleted, including a path inside it (`remote = provider:encrypted`). Values typed into the form are flattened onto one line for both `\n` and `\r`, so a field cannot introduce a config line for an INI reader that treats a bare carriage return as a line break.

- **The dashboard no longer stalls when there is a lot of stored backup data.** The "On disk" figure walked the entire backup tree inside the request handler, holding a mutex for the whole walk and recomputing at most once a minute — so the cost of opening the dashboard grew with the size of the fleet it was reporting on. Measured on a fast local disk with 200,000 files: **every cold dashboard load took 1.11 s**, and ten concurrent loads each waited the full walk because the walk held the lock. On a real backup volume on slower storage, while the lifecycle is reading the same disk, that is minutes of an unreachable dashboard — and the page that tells you backup health is the one that stops loading.
  The walk now runs in a background meter (`BACKITUP_STORAGE_REFRESH`, default `60s`) and handlers read an atomic, so a page load never touches the filesystem: the same ten concurrent loads took **20 ms wall**. Until the first measurement completes the row reads "measuring…" instead of a confident `0 B`.


### Security

- **One client can no longer fill the backup volume and stop every other client's backup.** `docker/sshd/backitup-recv` — the forced command the sshd container runs for every tar.gz upload — read its stdin into the client's directory with no limit at all, so a single host that was compromised or merely misconfigured (a source directory that grew, a runaway glob) could write until the shared `backups` volume was full. The blast radius was the whole fleet: every *other* client's backup then failed with `ENOSPC`, and the failure mode left a partial `.tar.gz.part` behind on the way. Two bounds now apply, both read before the write path: `BACKITUP_RECV_MAX_BYTES` (per-run byte cap, default 50 GiB) — an upload that exceeds it is aborted mid-stream, the partial archive is deleted and the run exits non-zero with a message naming the limit — and `BACKITUP_RECV_MIN_FREE_BYTES` (headroom floor, default 2 GiB), which refuses the snapshot outright when free space on the volume is below it *and* lowers the per-run cap to what is left above the reserve, so one run can never eat the headroom and then fail halfway. **What the operator sees:** the refused upload makes the client's own next write fail, so without care the run reported a bare `broken pipe`; the client's upload error now carries the server's stderr, so the run's log tail reads `write |1: broken pipe (server said: backitup-recv: upload exceeds BACKITUP_RECV_MAX_BYTES (…); aborted after … bytes, partial archive removed, no snapshot written)` — the limit, by name, on the dashboard that shows the failure. A limit that cannot be parsed stops the run instead of disabling the guard, and a SIGTERM (container restart, client disconnect) now removes the `.part` as well: pre-fix, the same interrupted upload was only cleaned up later by the lifecycle's orphan pruner. **Configuration:** both are whole byte counts set on the **sshd** service (`docker-compose.yml`, README configuration reference), and `0` disables either. They cannot arrive as environment variables: sshd starts every forced command with a fresh environment (and `PermitUserEnvironment` is off), so `docker/sshd/entrypoint.sh` writes them to `/etc/backitup/recv-limits`, which is what the script sources — a first cut that simply exported them into the container would have silently applied nothing. **Deliberately not included:** a per-client snapshot *count* cap; retention already prunes to the client's window and a count cap would fight it. The rsync path (`rrsync`) is unchanged by this entry.

- **A failed-login budget belongs to an account, not to an address.** The login limiter counted failures per client address alone (`ips map[string][]time.Time`, keyed by `realIP`), and on the pre-fix binary that had two measured consequences: ten wrong passwords from one address answered `429` to the **correct** password for the rest of the minute, and — since `realIP` reads `RemoteAddr` and never trusts `X-Forwarded-For`, a reverse proxy (the deployment the README recommends) presents every user as the proxy's own address — ten failures from one attacker locked out *every account on the fleet*, including the operator who opens the dashboard to see whether their backups are running. Failures are now tracked in two windows: per **(address, username)**, ten per minute, which is the budget that belongs to an account; and per **address** across all usernames, a hundred per minute, which is what still stops a password list sprayed through many usernames from one source. A correct password clears the pair's failures — the account proved itself from that address, so an attacker's earlier misses are not the owner's to carry — while the address's fan-out count deliberately survives it, because clearing that would let anyone holding one valid account reset their own spray budget. The per-address budget is ten times the per-account one on purpose: a shared proxy address, or an operator who mistypes a few usernames, must never reach it, and only a real spray does. **What an operator hits:** ten failed logins for one account from one address lock *that account, from that address*, out for the next minute — every other account keeps working, and the same account can still sign in from a different address. Memory stays bounded: `gc()` now sweeps both maps (and drops emptied buckets), and the sweep takes an explicit `now` so a test asserts the bound instead of waiting for the ticker; the per-address budget also caps how many pair keys one source can create per window. A store that does not answer is still not counted as a failed attempt (PR #26's classification), now asserted for both maps, and `realIP` is unchanged in what it trusts — `X-Forwarded-For` is still ignored, since honouring it would let an attacker mint a fresh bucket per request — but now falls back to the raw `RemoteAddr` when there is no port to strip rather than lumping every such request into one empty-string bucket.

- **`POST /clients/{name}/snapshots/bulk-delete` can no longer delete every snapshot a client has.** The `ids` form field was passed straight to the mode's `DeleteSnapshot` behind a single `strings.Contains(id, "..")` guard, so `ids=.` — which contains no `..` — reached `os.RemoveAll(filepath.Join(snapshotsDir, "."))`. `filepath.Join` cleans that to `snapshotsDir` itself, so one authenticated request removed every hot snapshot for the client *and* the `latest` symlink and then redirected as a success; the `latest` guard could never fire, because the symlink's target is a snapshot id, never `"."`. Reproduced against the pre-fix binary with two snapshots on disk: `ids=.` answered `303` and left the store empty. Snapshot ids are now validated in one place, `mode.ValidateSnapshotID`, which the bulk handler, the single-snapshot handler and both modes' `DeleteSnapshot` all go through, and which accepts only the filename shape the mode itself produces — `<ts>` for rsync, `backup-<ts>-<seq>.tar.gz` for tar.gz — so `.`, `..`, any path separator, a NUL, the `..` substring and any foreign name are refused. `DeleteSnapshot` additionally resolves the id through `mode.SnapshotPath`, which refuses anything that is not exactly one entry inside its base directory, so a caller that regresses still cannot resolve to a directory it owns and remove it. The bulk handler validates the whole batch *before* deleting: a request carrying one bad id now deletes nothing and answers `400`, where it used to answer `303` having deleted the rest of the batch. `latest` protection is unchanged. The rsync mode was the destructive path — the same `..`-only guard meant a direct `DeleteSnapshot(ctx, clientDir, "..")` removed the client directory itself (the oldest snapshot's `latest` readlink simply did not match), while tar.gz's `os.Remove(clientDir)` merely failed on a non-empty directory. **Status codes:** an invalid id in the bulk form is now `400` instead of a `303` success redirect, and the single-snapshot route answers `404` for an id that is not a name the mode could have produced (it already answered `404` for `..`); the success path for a real id is still `303`, which is the only one the web UI posts.

- **The crypt key is write-only and never leaves the server in a response.** The two key parts are obscured with `rclone obscure` on the way to stdin (never argv, so they cannot be read from `/proc/<pid>/cmdline` or `ps`) and stored obscured, like every other password in this app — there is no second mechanism. Neither the plaintext nor the obscured value is ever rendered: the edit form shows an empty `password` input with a "leave blank to keep the existing value" hint, the add form shows nothing, and a test asserts both values are absent from every response body (list, add, edit, client pages) and from a captured log buffer, and that the generated file is `0600` because it now holds key material.
- **Client directories can no longer be shared.** A client's storage directory was derived on the fly from its name, so names differing only in punctuation, spacing or case (`dup a`, `dup-a`, `Dup_A`, `dup/a`) produced one directory and one identical SSH forced command — two clients in one read-write jail, each able to download the other's data. A name with no alphanumeric characters (`..`, `.`, `/`) slugged to `""`, which jailed the client at the backup base directory itself. The slug is now a persisted, UNIQUE column (`clients.slug`), computed once on create and used for every directory path (`authorized_keys`, snapshot listing/download/delete, offsite object prefix, lifecycle pruning). `POST /clients` rejects an empty slug, a slug already in use, and a name longer than 63 characters (the name becomes the directory component and part of the sshd forced command) with a form error naming the conflict; `authkeys.Render` emits no line at all for a client whose slug is unusable, and the slug is validated against an allowlist (`^[a-z0-9][a-z0-9-]{0,62}$`) because it is embedded in `authorized_keys`. Existing databases are upgraded automatically: each row is backfilled from its name, the oldest client keeps the plain slug, later collisions get `-2`, `-3`, … and a slugless name falls back to `client-<id>`. **This separates future writes only — see the upgrade note below for clients that already shared a directory.**
- **Creating a client can no longer break SSH for the fleet, and deleting one can no longer leave its key live.** A backup directory that cannot be created (an over-long name made every `MkdirAll` fail) used to abort the whole `authorized_keys` rewrite, so after that point every create/rotate/delete only logged an error while the file stayed stale — a deleted client kept SSH write access. The name is now capped at 63 characters when the client is created, a directory failure is reported per client without blocking the rewrite, and a failed rewrite after a delete is shown to the operator as an error instead of a success redirect.
- **Deleting a user now ends their sessions.** Admin sessions were keyed only by the username string and never re-checked, so a deleted account kept full admin access until the 12-hour session TTL expired — enough to mint new client keys. Sessions are now bound to the user id, `postDeleteUser` revokes every session of the deleted account, and `requireAdmin` treats a session whose user no longer exists as invalid.

- **A client's own claim of success is no longer taken on trust.** `POST /api/v1/status` accepted `status`, `bytes`, `files` and `snapshot_id` from the bearer-token holder and stored them, so any host holding a valid client token could report a backup that never happened — with any size it liked — and the dashboard showed it as healthy. The token says *which* client is talking, not that anything was backed up. An `ok` is now corroborated server-side before it is recorded: the named snapshot must be listed in the client's own store (rsync: the snapshot directory; tar.gz: the archive, which must also be a non-empty regular file). A claim the server cannot match is recorded as `failed` with `unverified by server: <reason>` appended to its `log_tail` and a line in the server log; the wire protocol is unchanged and the client still receives its `run_id`. The bundled tar.gz client cannot name its archive at all — it streams to `backitup-recv`, which picks the filename server-side, so its report carries no `snapshot_id` — and for that shape the claim is corroborated by the upload itself: a non-empty archive must exist that was written during this run, with the window bounded at both ends (`max(started_at − 15m, now − 2h)`). The client's own `started_at` can only narrow that window, never widen it, because a backdated start would otherwise reach back to any archive the store already holds; the two-hour floor keeps a genuinely slow upload valid, since the archive's mtime is stamped when the upload finishes. Archive *contents* are not gunzipped here — that would read every archive on every report — so a corrupt-but-present archive is still caught by the lifecycle's offsite pass, which reads it anyway.
- **The dashboard no longer reports overlap as health.** Client health was derived from the newest run row, and an `overlap` row (cron fired while the previous backup was still running) fell through to "ok" — and refreshed the timestamp while doing it. A client whose backup had been overrunning its schedule for hours, and whose last real backup was hours old, therefore read "ok / just now", which is the case where the truth matters most. Health is now aged from the client's last **successful** run (`DeriveHealth` takes it explicitly; `LastSuccessfulRun` / `LastSuccessfulRunAllClients` supply it): a fresh overlap after an old success is `stale`, overlap-only history with no success yet is `never`, and only a success inside the cadence reads `ok`. The dashboard also names an overlap instead of presenting it as a backup (`overlap 2m ago`, no size), and the stale-alert pass uses the same rule.

### Fixed

- **The create-client and rotation pages now read as one set of instructions: one name per path, the source is called the source, a paste-ready cron entry, and a rotation that does not ask you to create a directory that already exists.** Six defects, all in the copy and structure of `client_created.html` and the strings `clients.go` generates, all found by reading the pages an operator actually gets. (1) Step 1 named `/etc/backitup/<name>/` while the command mounted `/PATH/TO/SECRETS`, and nothing equated the two: both now come from `secretsDir`, so the page names one path and the command mounts exactly that path (a secrets directory typed into the form is used for both, rather than the default). (2) The read-only source mount was labelled `/PATH/TO/BACKUP`, which reads like the destination: it now carries the client's own `source_label` when that looks like a path (`/mnt/photos`), otherwise `/path/to/source` with the page saying to replace it. (3) With `BACKITUP_SSH_HOST_KEY` unset the page still offered a Secure tab whose command mounted a `known_hosts` file the page never printed, a dead end presented as a choice: `dockerCmds` generates the verified variant only when the server can hand over that file, and the page renders the insecure command alone, saying what it gives up and how to configure the key to get a verified one. (4) The cron box held `30 2 * * *  # paste docker run command here`, so the operator had to assemble the real entry out of two boxes: each cron box is now one complete crontab entry, the schedule followed by the whole command with its continuations intact, and the page names the crontab file and says the schedule is the field to edit. (5) and (6) Rotation re-used the create copy verbatim, so it told the operator to create a directory that already holds the old key and re-issued `known_hosts` as though it had changed: the rotation page now says to overwrite `id`, that the old key and token stopped working immediately so the next cron run fails with `401 unauthorized`, that only the `BACKITUP_TOKEN` value in the existing line needs replacing, and that `known_hosts` is unchanged. The add-client form's live preview follows the same host-key rule, so the form cannot advertise a mount the created page will not show. Rendered-page tests cover both host-key states for create and rotate (`client_created_page_test.go`), unit tests prove the cron entry's command really reaches docker intact and that the secrets directory and source mount cannot produce two names for one path, and `docs/screenshots/client-created.png` is retaken alongside four new ones for the two host-key states of both pages.

- **A store that does not answer is reported as a timeout, not as bad input.** Every admin handler bounds its store work with a five-second deadline, and every one of them reported a *spent* deadline as whatever error it would otherwise have shown: `POST /clients` answered `400` with "Could not create client (is the name already taken?)", `POST /clients/{name}/rotate` answered `500` "rotate failed" and logged nothing at all, a timed-out session check redirected the admin to `/login` — a page that needs the same store to work — a timed-out token lookup told a backup client its token was bad (`401`, which invites a re-enrol for a server-side hiccup), and a timed-out login was counted as a failed password, so ten store blips locked the operator out of the server that had the fault. On a loaded CI runner a five-second stall was therefore indistinguishable from a product bug: builds 163 and 165 failed on `create status = 400` / `rotate status = 500` while the identical commit's paired PR build passed. A deadline, a request cancelled mid-flight and SQLite's own "database is locked" are now classified together, logged with the underlying error and the bound that expired, and answered `503` + `Retry-After` — the request did nothing, retry. Genuine store errors keep their handler's own `500` (or rendered form error) and are logged too, so an unexplained 500 cannot happen again. The bound is one field (`Server.dbTimeout`, still 5s), which lets the timeout path be tested with a deadline that has already passed instead of waiting for a machine to stall — and the test fixtures no longer assert, silently, that the runner never stalls for five seconds.
- **Creating a client can no longer leave it unable to connect.** `POST /clients` rewrote `authorized_keys` under the request's store context, so when `CreateClient` came close to the deadline the rewrite was skipped: the operator was shown the new key and token for a client that sshd had never heard of. The rewrite now runs on its own bounded context (as rotation and deletion already did), and a failure says in the log that the key is not in the file yet instead of reading as a generic regenerate error.
- **A client that only ever overlaps can no longer read healthy**, and an overlap is labelled as such on the dashboard instead of being shown as the newest backup. See the security entry above for the mechanism.
- **Retention actually runs when the source does not change.** A deduplicated offsite upload was skipped without being recorded, so the snapshot never became "offsited" and the hot pruner protected it **forever** — an unchanged directory grew the hot store by one snapshot per run, whatever `retention_days` said. The duplicate is now recorded as a dedup row (`offsite_objects.dedup_of`, additive migration) that names the remote object already holding that content: the snapshot may be pruned, offsite verification checks that real object instead of a path that was never uploaded, the offsite pruner never counts a dedup row as the newest object (which would have made the real object of that content deletable), and deleting an object removes the dedup rows that pointed at it. A dedup record protects a hot snapshot only while the object it names is believed present, and neither does a record whose object the verification pass reported `remote_missing` — "offsited" now means "the content is somewhere else", not "was uploaded once". The client page lists them nowhere: they are records, not objects, so it offers no Download or Delete for a path that was never uploaded.
- **A failed prune is no longer reported as a clean pass.** `pruneHot` logged and swallowed delete errors, returned nothing, and so `RunOnce` reported success while the hot store kept everything the pruner could not remove. It now returns `deleted`/`failed` counts and the first error: the counts are logged per client and a failure makes the lifecycle pass return it (verification and alerting still run first).
- **A corrupt timestamp can no longer delete a recent offsite object.** Every timestamp column was parsed with `x, _ = time.Parse(...)`, so a malformed `uploaded_at` became year 1 — older than every horizon — and offsite pruning deleted the object as "ancient". Offsite rows that cannot be dated are now skipped with a loud log (the row is kept, and kept out of the pruner's reach), and the upload schedule skips over them instead of stopping — `LatestOffsite` used to hand its parse error to the scheduler, which logged and skipped the client, silently ending that client's offsite copies. The remaining parse sites are explicit too (`parseStoredTime`/`displayTime`), so no discarded error is left in the store.
- **Offsite staging no longer fills the system temp dir.** rsync archives were written with `os.CreateTemp("")` — the system temp dir, often a small tmpfs — and every archive of a pass was removed only when the pass ended, i.e. N × snapshot size of scratch. They now go to `BACKITUP_STAGING_DIR` (default `<backup dir>/staging`) and are removed as soon as each upload finishes.
- **An interrupted schema upgrade can no longer discard the run history.** Schema evolution was a list of independent statements, and "has this already been applied?" was decided by matching the text of an error (`duplicate column name`) — a technique that cannot work for anything but `ADD COLUMN`. The rebuild of `runs` ran `CREATE TABLE runs_new` / `INSERT … SELECT *` / `DROP TABLE runs` / `ALTER TABLE runs_new RENAME TO runs` as four separate commits, so a crash between the drop and the rename (a restart, an OOM kill, a full disk) left every run stranded in `runs_new` and nothing in `runs`: reproduced against the pre-fix binary, three runs became `runs = 0 | runs_new = 3`, and the dashboard started again from an empty history. Migrations are now one transaction per step, gated by `PRAGMA user_version` — the version stamp commits in the same transaction as the step's work, so it can never claim work that did not commit — and a step is skipped entirely when the database is already at it, which also makes a second `Open()` a no-op. The `runs` rebuild is part of that transaction, so it either happens completely or not at all; the test injects a crash at the exact point that used to lose the data and asserts the rows are still there on the next start.
- **`schema.sql` is now the only definition of the schema, and a fresh database has the same columns in the same physical order as an upgraded one.** They used to disagree: `schema.sql` declared the client columns in one order with `slug`/`version`/`skip_symlinks` inline, while an upgraded database had those appended at the end of the table plus four more (`token_prefix`, `offsite_upload_mode`, `disable_offsite_pruning`, `offsite_cron`), and `users`/`remotes`/`offsite_runs` existed only as DDL strings inside `store.go`. The `runs` rebuild copied rows with `INSERT INTO runs_new SELECT * FROM runs`, which silently depends on the two sides agreeing — that is a trapdoor, not a guarantee. Missing tables now come from `schema.sql`, and any table whose stored definition differs from the file is rebuilt by the SQLite table swap inside the migration transaction, copying columns by name in the file's order; an unexpected extra column is refused rather than dropped. The schema comments were stale in two places too: `log_tail` is capped at `model.MaxLogTail` (64 KB), not the 4 KB the schema and the model comment still claimed. A test builds a database at the pre-`running` shape, migrates it, and asserts that both the column set and the `PRAGMA table_info` order of every table match a freshly created database, with the three runs and the offsite record intact.

### Upgrade notes

- **The first start after this upgrade drops two columns from `clients`.** `offsite_retention_days` and `disable_offsite_pruning` are removed by the schema migration (one transaction, `user_version` 3), because offsite retention now belongs to the B2 bucket's lifecycle rule. Nothing else in the database depended on them, and no other column, row or index changes: the client rows keep every other setting, and their runs and offsite records are untouched. The upgrade is one-way — an older backitup refuses this database rather than reintroducing the columns. **After upgrading, set the expiry rule in the B2 console** if you were relying on `offsite_retention_days`: with no rule, nothing in the bucket expires, and with a name-pattern rule against a `crypt` remote nothing expires either (the names are ciphertext — use days-since-upload). The startup line `lifecycle: offsite retention is delegated to the B2 bucket lifecycle rule; backitup will not delete offsite objects` is the marker that this build is running.

- **The client-directory split is forward-only; pre-existing colliding clients keep sharing one directory.** Before this release a client's directory came from its name, so two clients whose names slugged alike (`dup a` and `dup-a`) wrote into *one* directory. The migration gives the later client a new slug, which changes where it writes *from now on*, but it cannot move its history: snapshots in that directory were written by one ssh user with timestamp-only ids, so they are not attributable to either client, and an automatic move would guess and could delete data. Left as-is, the client that kept the plain slug still reads and writes the shared directory and prunes it under its own retention policy, and the other client's existing snapshots there are stranded (never listed, pruned or uploaded again); its offsite default prefix also changes (`dup-a` → `dup-a-2`), so its existing cold objects are reported `remote_missing`. **On upgrade, check the server log for `WARNING: legacy client slug collision`** — one line per affected pair, naming both clients, the retained slug, the new slug and the shared directory. To quarantine it: stop the server, rename that directory aside (e.g. `mv /srv/backups/dup-a /srv/backups/dup-a.quarantine`), start the server so the remaining client begins with an empty directory, then inspect the renamed copy by hand and re-upload whichever client's data you keep.
- **The first start after this upgrade rewrites the database schema once.** Every table whose stored definition differs from `schema.sql` is rebuilt (create, copy, drop, rename) inside a single transaction, and the indexes are created afterwards; nothing is written outside that transaction, so a start that is interrupted leaves the database exactly as it was and simply retries next time. On a large `runs` history expect this start to take a moment on the first run and nothing on every run after it. A database written by a *newer* backitup is refused with a message saying so, rather than being "migrated" backwards by an older binary.

## [0.1.0.0] - 2026-06-22

### Added

- **Credential rotation** — admins can now regenerate an existing client's SSH keypair and bearer token from the client detail page (`POST /clients/{id}/rotate`). The old credentials are invalidated atomically; run history and all other settings are preserved.
- Rotation result page re-uses the one-time secrets display, showing the new private key, token, and cron line — with a visible warning when the SSH `authorized_keys` file could not be updated immediately (credentials remain valid in the database; `authorized_keys` self-heals on next client edit or server restart).
- Schema migration: a `version` column (INTEGER NOT NULL DEFAULT 1) is added to the clients table. Existing databases are upgraded automatically on first startup. This column guards against double-submit races by using compare-and-swap semantics on every rotation — a 409 Conflict is returned when two concurrent rotation requests are detected.

### Changed

- SSH key generation and token hashing extracted into a shared `generateClientCreds` helper used by both client creation and rotation, eliminating duplicate credential-generation code.
- The `RotateClientCreds` store method now accepts the caller's observed `version` and only updates the row when it matches, incrementing the version atomically on success.
